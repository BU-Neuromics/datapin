# Implementation decisions (post-handoff)

Continues the numbering from `docs/datapin-handoff.md` §2 (D1–D10). These
were made autonomously during the feature-complete build-out (2026-08-10,
maintainer instruction: "work autonomously… make opinionated decisions if
needed, recording them for review later"). Flag any of these for revision in
review; none are load-bearing beyond the code that cites them.

| # | Decision | Rationale |
|---|---|---|
| D11 | **Feature-complete scope = plan §8 Phases 1–3** (core+Zenodo, metadata/FAIR floor, site generator). Figshare/Dataverse (Phase 4) and Phase 5 breadth deferred; `check --fair` (F-UJI) kept in scope as a Phase 2 item. | Maintainer tabled OSF migration and said "focus on Zenodo"; a second archive backend adds breadth, not depth. The cross-adapter contract suite still lands (parameterized over fakeinvenio + sandbox) so Phase 4 has rails. |
| D12 | **OSF is NOT refactored behind the Backend interface yet.** Existing OSF sync paths (`push/pull/sync/status` on `[[files]]`/`[[wikis]]`) stay as-is; the `Backend` interface serves archive backends (invenio) now. | Maintainer: "table any OSF migration and just focus on zenodo." The refactor is mechanical but wide; doing it while introducing the interface doubles the blast radius. Plan §4.7's workspace-role architecture is unchanged — this only re-orders work. |
| D13 | **Manifest schema 2 = schema 1 + `[[datasets]]`.** `[[files]]`/`[[wikis]]` remain valid at schema 2 and keep their OSF semantics; datasets are additive. A schema-1 file (no `schema` key) loads identically. | Keeps every existing workflow running through the pivot with no `migrate` step (which is tabled with OSF work). Cross-section duplicate-`local` validation extends to datasets. |
| D14 | **Generalized retry lives in new `internal/httpx`; OSF's `internal/client/retry.go` is left untouched.** The invenio driver uses httpx (Retry-After first, then `X-RateLimit-Reset`, injectable sleep/clock, decline-don't-truncate). | Sharing one implementation would mean touching stable OSF code mid-pivot. httpx is the carry-over target when OSF is eventually adapterized (D12). |
| D15 | **`Retry-After` is only honored on retryable statuses.** Sandbox sends `retry-after` on 200s too (see `docs/zenodo-notes.md` §3) — the retry layer keys on status code, never header presence. | Spike finding; encoding it as a rule prevents a subtle stall bug. |
| D16 | **`backend.Metadata` is a struct now, superseded by `internal/meta` in Phase 2.** Phase 1 publishes with the DataCite floor (title, publisher, publication date, creators, resource type, license, description, keywords); Phase 2's model serializes into it. | Avoids blocking the publish transaction on the full metadata subsystem. |
| D17 | **fakeinvenio defaults mirror observed sandbox behavior** (empty files accepted, hybrid legacy/RDM response shapes, idempotent `POST /versions`, atomic 100-file cap at registration, `retry-after` on 200s). Strictness/divergence knobs are opt-in per test. | The fake encodes our assumptions; the assumptions are the fixtures. |
| D18 | **Publish reconciles inside the driver.** On a 5xx/timeout from the publish action, `invenio.Publish` re-GETs the record and returns success iff `status == published` (spike: publish-twice → 404, publish can 504 while succeeding). Callers see one clean result. | Centralizes the trickiest recovery rule so every command gets it right. |
| D19 | **Zenodo legacy/RDM hybrid responses are read defensively**: DOIs read from `pids.doi.identifier` first, then top-level `doi`/`conceptdoi`. | Spike finding: sandbox publish/draft responses are legacy-shaped. |
| D20 | **Default license suggestion: CC0-1.0** (the open item in handoff §2), presented as a suggestion with CC-BY-4.0 as the named alternative; `check` warns on NC/ND. | Plan §2.2 already leans CC0 for data (Dryad precedent, attribution stacking); wording-only decision, easily reversed. |

## Phase 3 additions

| # | Decision | Rationale |

| D25 | **Site pipeline ships goldmark + GFM + frontmatter only**; chroma highlighting, mermaid, and KaTeX (named in plan §2.6) are deferred as theme enhancements. ## Phase 4 additions (second and third archive backends)

| # | Decision | Rationale |
|---|---|---|
| D28 | **fakefigshare and fakedataverse encode DOCUMENTED behavior, not live-verified behavior** — no credentials were available. Both fakes and drivers carry an "unverified against live" marker; live tiers exist (`integration/livefigshare` pattern to follow) and skip without credentials. The first live run against each service should be treated as a Phase-0-style spike: expect divergences (the Zenodo oc-checksum lesson) and fix fake+driver together. | Maintainer: "implement the backends, though I can't provide live services for testing yet." |
| D29 | **A Dataverse remote's collection alias rides on the URL path** (`https://host/dataverse/<alias>`), defaulting to `root`. | Keeps config.Remote at kind+url without a per-kind options bag; matches how Dataverse users see collections. |
| D30 | **`Caps.PerVersionDOI` added**: Zenodo/Figshare mint per-version DOIs; Dataverse has one DOI for all versions (version picker on the landing page). The contract suite and pins handle both; `versions <slug>` shows the same DOI per row on Dataverse remotes. | The interface must not assume Zenodo's DOI model — this is exactly the drift the contract suite exists to catch. |
| D31 | **Figshare/Dataverse model "new version" as the mutable account draft** (ImportsPrevious=false): the draft retains published files, so the publish transaction skips files-import and the per-key plan converges on whatever state the draft is in (upload replaces same-name entries idempotently). | Matches both platforms' actual lifecycle; keeps the transaction crash-re-runnable everywhere. |

## Phase 5 additions (workspace backends)

| # | Decision | Rationale |
|---|---|---|
| D32 | **Workspace sync operates at the dataset level**: `datapin push <slug>` / `pull <slug> --workspace` move a dataset's files to/from its `workspace` remote (dataset field or `default_workspace`). The schema-1 `[[files]]` OSF flow is untouched. | Retrofitting arbitrary workspace remotes into the OSF-shaped `[[files]]` entries would have forked their semantics; datasets already group "the outputs that travel together", which is what the founding cluster→laptop use case moves. Revisit if per-file workspace tracking is wanted. |
| D33 | **Remote kind implies role**: `dir`/`s3`/`sftp` are workspace kinds, `invenio`/`figshare`/`dataverse` are archive kinds. No separate role field in config. | One word says both; a kind that could serve both roles doesn't exist in the current set. |
| D34 | **S3 remote URL form is `s3://<endpoint>/<bucket>[/<prefix>]`** (`?insecure=true` for plain-HTTP MinIO, `?region=`); credentials are the per-remote token as `ACCESSKEY:SECRETKEY`, falling back to `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`. A `dir` remote is a plain path (mounted NAS). | Endpoint-in-URL serves the actual audience (institutional MinIO/R2, not AWS-default); reusing the token ladder avoids a second credential mechanism. |
| D35 | **The journal layer is generic** (`internal/workspace` over a 6-method Store); localdir/S3/SFTP get identical versioning semantics, tested once against the real protocols (in-process SFTP server, gofakes3). Native-scheme remotes (versioned S3 buckets) remain future work — every current remote uses the `datapin` scheme. | One implementation of the D4 invariant instead of three; the Store surface is small enough that a new workspace backend is ~200 lines. |
| D36 | **Out-of-band overwrites are archived, not just detected**: when the observed object disagrees with the journal head, its bytes are archived under their own content address before the push proceeds, and the event records the fact. | Strictly better than the plan's minimum (detect + report unrecoverable): bytes someone scp'd over a tracked file are usually bytes someone cared about. |

## License policy (post-first-live-Dataverse-run)

| # | Decision | Rationale |
|---|---|---|
| D37 | **A license is required at the publish boundary and is always an explicit user choice** (maintainer decision, 2026-08-11; revises D20's posture). `datapin check` keeps a missing license as a warning (drafting is fine without one); `publishPreflight` refuses to publish without one; the publish confirmation plan displays the license next to the PUBLIC/PERMANENT warning. CC0-1.0/CC-BY-4.0 remain *suggestions in wording only* — datapin never fills a license in, and drivers never substitute one: Dataverse resolves the manifest's SPDX id against the instance's `/api/licenses` registry (`rightsIdentifier` crosswalk first, then normalized name) and errors listing what the instance offers; Figshare's previously-silent drop of unmappable ids is now the same loud, typed error. | The first live Dataverse run (live CI on demo.dataverse.org 6.11) rejected raw SPDX ids — per-instance license registries are real. And a licenseless publish isn't neutral: the backend applies its own default (demo's is CC0), granting rights the user never chose. Publishing is the permanent, public boundary where completeness is already enforced; a legal rights grant belongs behind it. |
| D38 | **`contact_email` in `[datasets.metadata]`, required by the dataverse driver.** Dataverse's citation block mandates a Point of Contact e-mail (live-verified 403: "Validation Failed: Point of Contact E-mail is required."); datapin has no e-mail to invent, so the field is user-supplied dataset metadata, the dataverse driver fails with the manifest key when it is absent (before anything is created), and fakedataverse enforces presence with the live error text. Other backends ignore the field; `check` does not require it (it matters only for Dataverse targets). | Second live-run divergence in the same D28 spike. Dataset metadata (not per-remote config) is the right home: the contact belongs to the data, and it serializes naturally through `backend.Metadata`. |
| D39 | **Dataverse uploads always send `"tabIngest": false`, and the driver waits out dataset locks (bounded poll of `/locks`) before mutations and publish.** Live-verified: publishing right after a CSV upload 403s ("This dataset is locked. Reason: Ingest.") because Dataverse ingests tabular files asynchronously — and ingest also *rewrites* the file (`data.csv` → `data.tab`, new checksums). fakedataverse models the ingest lock as never-clearing (the driver must disable ingest, not wait it out) plus a `SetLock` hook for clearing locks (post-publish DOI finalization). | datapin's contract is byte fidelity: the bytes pinned are the bytes served back, MD5-verified. Ingest breaks both the transaction (lock) and the pin (rewrite). The lock-wait covers Dataverse's other async locks at the publish/upload boundaries. |
| D40 | **Dataverse publish reconciles by polling for released-version-count growth.** The publish POST is accepted while DOI finalization completes asynchronously (live-verified: an immediate re-GET still shows the version unreleased), so `Publish` records the released count before the POST and polls (bounded, same budget as the lock wait) until it grows — "some version is released" is already true when publishing v2 over v1, which is exactly the bug the async fake caught. A publication that never finalizes is a bounded, explained error (the previous code wrapped a nil error: `%!w(<nil>)`). fakedataverse models publish as asynchronous (finalization completes after N dataset GETs, `SetPublishFinalizePolls` to tune/never). | Same D18 lesson as invenio, Dataverse-shaped: the driver owns the trickiest recovery rule so every command sees one clean result. |
| D41 | **Dataverse implicit-draft semantics + the pull pin gate.** Live-verified triple divergence behind "pull restored v1's bytes": (1) a released dataset has no readable `:draft` version until a mutation lazily opens one — the read 404s, so the transaction's replace-delete silently no-opped (`DeleteDraftFile` treats NotFound as already-gone); (2) Dataverse does not reject a duplicate upload label — it silently renames (`data.csv` → `data-1.csv`), publishing v1's file at the tracked key beside a mis-keyed v2; (3) datapin's pinned pull verified stream-vs-listing and overwrote the pin, delivering wrong bytes without complaint. Fixes: `draftFileEntries` falls back to `:latest-published` when `:draft` 404s (that is exactly what the first mutation seeds the draft with); `UploadFile` deletes an existing same-key draft entry before adding (idempotent replace, no rename possible) and errors loudly if the server renamed anyway; `runDatasetPull` fails hard when the listing checksum contradicts a pinned MD5 (`--latest` re-pins deliberately). fakedataverse now 404s pre-mutation `:draft` reads and models the rename. Bonus hermeticity fix: the integration harness severs `DBUS_SESSION_BUS_ADDRESS` so a locked desktop keyring can never park the binary on a Secret Service prompt (the token ladder reads env > keychain > file). | The pin is datapin's contract; every layer that can contradict it must fail loudly, not converge silently. |
| D42 | **Version chains are sorted, never trusted from listing order.** Real Dataverse lists versions newest-first (draft first when present); the fake modeled oldest-first, and the driver built `Record.Versions` in listing order — so publishing v2 pinned `@1` as the result (caught live by the D41 pull pin gate, checksum mismatch). The driver now sorts released versions by number; the contract suite asserts oldest-first `Record.Versions` and that publish returns the newest version's id, for every adapter; fakedataverse lists newest-first like the real service. | Listing order is backend trivia; `Record.Versions` order is API contract. The contract test is what keeps the other adapters from regressing the same way. |

## Multipart uploads in the invenio driver (issue #19)

| # | Decision | Rationale |
|---|---|---|
| D43 | **Threshold-gated multipart uploads, serial parts, no expiry handling.** `invenio.UploadFile` switches to the multipart `M` transfer when `size > multipartThreshold`; both the threshold and the part size are injectable Client fields (`WithMultipartThreshold`/`WithPartSize`), defaulting to 100 MiB each. The flow is register `{"transfer":{"type":"M","parts":N,"part_size":S}}` → PUT each part to its `links.parts[]` URL → POST commit, matching InvenioRDM's multipart transfer provider (invenio-records-resources) and fixture 39. Parts upload **serially**: the `Backend` interface hands the driver an `io.Reader`, not an `io.ReaderAt`, and widening the interface for one driver's parallelism isn't worth it yet. The part URLs' ~14-day expirations are ignored — they are minted immediately before use, and a crashed run's pending entry is cleared by publish preflight (never resumed), so re-registration-on-expiry (issue #19's bullet) is unreachable dead code today; revisit if resumable uploads ever land. Below the threshold the single-PUT path is byte-for-byte unchanged. | The spike verified only registration (fixture 39, the sandbox draft was discarded before any part moved); the smallest correct implementation follows the documented provider. Injectable knobs are what let the hermetic tests and the cheap live probe cross the threshold with small files. |
| D44 | **Multipart commit checksums are verified only when the server reports an md5; otherwise the driver surfaces NO checksum.** InvenioRDM's provider may return no checksum at multipart commit, or the placeholder `multipart:{etag}-{part_size}` while a background task recomputes the real digest. A non-md5 checksum is dropped from the returned `FileInfo` rather than passed through (the s3ws precedent: no checksum beats a wrong one); an md5 that mismatches the local sum still fails loudly like the single-PUT path. fakeinvenio's `AsyncMultipartChecksum` knob models the placeholder. | The manifest pin is the local MD5 either way, so nothing downstream depends on the commit checksum; passing a placeholder through would poison comparisons that assume `Checksum.Algo == "md5"`. |
| D45 | **Any multipart failure after registration aborts by deleting the pending entry, under a cancellation-immune context.** A failed part PUT, a failed commit, malformed part links, or a checksum mismatch all `DeleteDraftFile` the key (best-effort, `context.WithoutCancel` + 30s bound) before returning the error — the server-side multipart abort rides on that DELETE. The draft therefore never retains a pending entry that would block publish, even when the failure was Ctrl-C mid-part. | A registered-but-uncommitted entry blocks publish (fixture 22); the single-PUT path can rely on publish preflight to clear strays, but multipart failures are common enough (big files, long transfers) that leaving garbage on every abort would make preflight cleanup the normal path instead of the recovery path. |

## Migrate additions (OSF sunset exit ramp, issue #30)

| # | Decision | Rationale |
|---|---|---|
| D46 | **`migrate` scaffolds with TODO markers instead of prompting for metadata.** The issue's "prompt for the DataCite floor" step is replaced by a literal `TODO` sentinel for license and contact_email (and a missing title), creators as name-only skeletons, and a TODO checklist in the summary/`MIGRATED.md`. The sentinel is deliberately invalid where it appears — `TODO` is not an SPDX id, so `datapin check` errors and `publishPreflight` (D37) refuses — meaning an unreviewed migration can never publish by accident. In `--output=json` mode (and non-dry-run only) remaining TODOs exit 1, per the issue's "exit code signals incompleteness"; text mode exits 0 with a loud warning, so scripted exports don't read a successful export as a failure. | The issue itself says migrate needs "an honest skeleton with loud TODOs", not publishable metadata; `datapin check` stays the single completeness gate. A field-by-field interactive wizard can be added later without changing the contract. |
| D47 | **The OSF node license is never mapped — license is always a TODO.** Even when the node has a license set, migrate does not copy it into the manifest. | D37 made a license an explicit user choice at the publish boundary, never something datapin fills in; OSF license objects (incl. "Other"/custom text) don't map reliably onto SPDX ids, and a silently wrong rights grant is worse than a loud TODO. This deliberately narrows the issue's "license if it maps to an SPDX id" row. |
| D48 | **Idempotent re-run = per-slug merge, and GUID mode refuses a `[[files]]` manifest.** Re-running GUID mode skips MD5-identical files and carries forward, per dataset slug, everything the user may have touched: the whole metadata block, publish pins (record/concept/DOIs/version), archive/workspace assignments, site config, and user-added datasets/pages. A dest whose manifest still has `[[files]]`/`[[wikis]]` errors with a pointer at manifest mode — the two modes must not stack. | "Resumable and idempotent" is a goal in the issue; preserving user edits is what makes re-running safe after the user has started reviewing metadata. |
| D49 | **Manifest-mode grouping and keys**: default one dataset per top-level directory with repo-root files under slug `root`; `--dataset <slug>=<glob>` overrides claim files first (path.Match plus `/**`-prefix and bare-directory conveniences); dataset file keys are the full slash-separated local path (GUID mode: the path within the node); wiki entries keep their existing local paths as site pages (the `docs/<page>.md` convention applies to GUID mode, which has no locals to preserve). AHEAD_OF_MANIFEST entries are kept as-is — local is the going-forward truth and migrate never uploads. DIVERGED still fails hard pre-flight (resolve via `datapin sync --resolve=…` first). | Grouping default follows the issue's lead; full-path keys are collision-free and survive the flat-key model of every archive backend (Dataverse turns them into directoryLabels). Moving manifest-mode wiki files into docs/ would churn users' repos for zero information. |
| D50 | **`--components` exports the whole component tree recursively**, each component as its own dataset under its (deduped) slug directory, with its own contributors, `IsDerivedFrom` link, and `<component>/docs/` wiki pages with slug-prefixed site entries. Default remains root-only with a per-component notice + `components_skipped` in JSON. | The issue names one level but nested components are common on OSF; stopping at depth 1 would silently strand grandchildren of exactly the projects most in need of the exit ramp. |
| D51 | **Manifest-mode confirmation is TTY-only.** An interactive terminal gets a plan + y/N confirm before the manifest rewrite (`--yes` skips); non-TTY and `--output=json` runs proceed without prompting (JSON "implies no prompts" per the issue). | The rewrite is atomic and the old manifest is one `git checkout` away; requiring `--yes` on non-TTY would break the issue's scripted/CI use while protecting nothing irreversible. Contrast with `rm`/bare `push`, which mutate *remote* state. |
| D52 | **Zenodo sandbox denies token-authenticated multipart part PUTs (live-verified, three rounds, 2026-08-11 — issue #46).** The part URLs the sandbox mints are same-host API URLs, not pre-signed object storage; registration succeeds but every part PUT 403s `"Permission denied."` regardless of headers. The driver keeps the documented InvenioRDM v13 protocol (correct for institutional instances) and the #44/#45 header rules (correct for genuinely pre-signed instances, harmless same-host); the live multipart test skips loudly on exactly that denial signature and fails on anything else, so it self-arms the moment Zenodo enables part uploads. | Blocking the whole live suite on a server-side gate we cannot change would hide real regressions behind a known red; a signature-scoped skip keeps both the signal and the honesty. |
